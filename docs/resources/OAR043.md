OpenAPI definition contains structural errors that would be detected by a strict parser or validator.

This rule validates a specific, detectable subset of structural errors: invalid `in` values on parameters, across `paths`, `components.parameters`, `webhooks`, and `components.pathItems`; and, for OpenAPI 2.0 and 3.0 documents only, invalid `type` values on parameter schemas.

Allowed `in` values for OpenAPI 2 (Swagger): `query`, `header`, `path`, `formData`, `body`.

Allowed `in` values for OpenAPI 3.0 and 3.1: `path`, `query`, `header`, `cookie`.

Allowed `in` values for OpenAPI 3.2: `path`, `query`, `querystring`, `header`, `cookie` (OpenAPI 3.2 adds `querystring` as a new valid value).

Allowed `type` values for OpenAPI 2.0 and 3.0 parameter schemas: `object`, `string`, `number`, `integer`, `boolean`, `array`, `null`.

**Scope notes**:
- This rule does not detect a document that fails to parse at all (malformed YAML/JSON syntax) — Spectral does not run any ruleset against a document its own parser cannot load, so that class of error is outside what a Spectral rule can report. Duplicate YAML keys are silently overwritten by Spectral's YAML parser and are not detected either. Sonar's `OAR043` does report both of those cases because it runs at the parser/grammar level, not as a lint rule over an already-parsed document.
- This rule does not validate `type` at all for OpenAPI 3.1 or 3.2 documents (neither a scalar value like `type: float` nor the entries of an array/nullable form like `type: [string, null]`). This matches Sonar's own OAS 3.1/3.2 grammar, which does not enforce the `type` enum either — confirmed empirically across every parameter surface (`paths`, `webhooks`, `components.pathItems`, `components.parameters`). Enforcing it in Spectral for those versions would flag documents Sonar does not, so a `type` written as `[string, "null"]` (or any other array/scalar value) is always accepted for OpenAPI 3.1/3.2.

Noncompliant Code Example (OpenAPI 3.0 — invalid "in")
---------------------------------------------------------------------------------------

openapi: "3.0.0"
info:
  title: Example API
  version: "1.0.0"
paths:
  /orders:
    get:
      parameters:
      - name: status
        in: headers
        schema:
          type: string
      responses:
        "200":
          description: OK

Compliant Solution
---------------------------------------------------------------------------------------

openapi: "3.0.0"
info:
  title: Example API
  version: "1.0.0"
paths:
  /orders:
    get:
      parameters:
      - name: status
        in: query
        schema:
          type: string
      responses:
        "200":
          description: OK
