OpenAPI definition contains structural errors that would be detected by a strict parser or validator.

Allowed `in` values for OpenAPI 2 (Swagger): `query`, `header`, `path`, `formData`, `body`.

Allowed `in` values for OpenAPI 3.0 and 3.1: `path`, `query`, `header`, `cookie`.

Allowed `in` values for OpenAPI 3.2: `path`, `query`, `querystring`, `header`, `cookie` (OpenAPI 3.2 adds `querystring` as a new valid value).

Allowed `type` values for OpenAPI 2.0 and 3.0 parameter schemas: `object`, `string`, `number`, `integer`, `boolean`, `array`, `null`.

Noncompliant Code Example (OpenAPI 3.0 — invalid "in")
---------------------------------------------------------------------------------------

openapi: "3.0.0"
info:
  title: Example API
  version: "1.0.0"
paths:
  /orders:
    get:
      parameters:
      - name: status
        in: headers
        schema:
          type: string
      responses:
        "200":
          description: OK

Compliant Solution
---------------------------------------------------------------------------------------

openapi: "3.0.0"
info:
  title: Example API
  version: "1.0.0"
paths:
  /orders:
    get:
      parameters:
      - name: status
        in: query
        schema:
          type: string
      responses:
        "200":
          description: OK

Compliant Solution (OpenAPI 3.1 — "type" is never validated)
---------------------------------------------------------------------------------------

openapi: "3.1.0"
info:
  title: Example API
  version: "1.0.0"
paths:
  /orders:
    get:
      parameters:
      - name: status
        in: query
        schema:
          type: [string, "null"]
      responses:
        "200":
          description: OK

---------------------------------------------------------------------------------------

openapi: "3.2.0"
info:
  title: Example API
  version: "1.0.0"
paths:
  /orders:
    get:
      parameters:
      - name: status
        in: querystring
        schema:
          type: string
      responses:
        "200":
          description: OK
